# Mobile E2E Testing Framework Decision

## Recommendation

**Use Maestro** for mobile end-to-end testing.

Maestro is the only framework that is officially recommended by Expo, works out of the box with Expo managed workflow, and has the lowest setup and maintenance burden. Detox explicitly disclaims Expo support, and Appium is overengineered for a single React Native app.

## Context

`apps/web` has Playwright for web E2E, but that only drives a browser. The mobile app (`apps/mobile` — Expo SDK 56, React Native 0.85.3, Expo Router, Clerk auth) has zero test coverage. We need to pick one framework before investing in writing flows.

## Comparison

| Dimension | Maestro | Detox | Appium |
|---|---|---|---|
| **Expo compatibility** | Officially recommended by Expo. Black-box tool — works with any `.app`/`.apk`, doesn't care about build system. General Expo issues are rejected from their issue tracker. | Framework-agnostic, so it works — but requires significant manual configuration for React Native apps. |
| **Setup complexity** | `brew install maestro`, write a `.yaml` file, run `maestro test`. No build plugins, no test runner config, no native code changes. | Requires a custom native build, Jest test runner config, Detox build config, and a detox-cli setup.◊ | Heaviest setup: Appium server, WebDriver client, capabilities config, platform-specific drivers.|
| **Test authoring** | YAML flows — sequential steps like `tapOn`, `inputText`, `assertVisible`. Readable by anyone, no programming required. | JavaScript/TypeScript with Jest. More expressive for complex logic, but more code to write and maintain. | Any language (JS, Python, Java, etc.) via WebDriver protocol.|
| **AI-friendliness** | Very high — YAML flows are trivially generated by AI assistants. Minimal syntax, no imports, no framework knowledge needed. | Moderate — standard JS test code, AI can write it but needs framework-specific knowledge (element matchers, synchronization). | Low — complex setup, verbose selectors, platform-specific capabilities make generation error-prone. |

Occasional flakiness on slow animations. | Gray-box with built-in synchronization — theoretically the most deterministic. ## Decision Rationale

### Why Maestro

1. **Expo officially recommends it.** This is the strongest signal. When your framework vendor says "use this tool," it means they test against it, document it, and will help when things break.

2. **Black-box approach eliminates integration risk.** Maestro doesn't hook into React Native internals or Expo's runtime. It talks to the device screen. This means Expo SDK upgrades, React Native version bumps, and NativeWind changes won't break your test infrastructure.

3. **Lowest total cost of ownership.** YAML flows are 5-10 lines for a typical screen interaction. No test runner to configure, no build plugin to maintain, no JS test framework to keep updated.

4. **`maestro studio` for test authoring.** The interactive recorder lets you tap through the app on a simulator and it generates the YAML — useful for quickly scaffolding flows.

### Why not Detox

Detox is a well-respected tool for pure React Native projects, but it explicitly disclaims Expo support:

> "Expo support with Detox is entirely a community driven effort. We have no specific support in Detox for Expo applications (ejected or otherwise). General Expo issues will no longer be allowed in the Detox issue tracker."

For an Expo managed workflow app on SDK 56, this is a dealbreaker. If a Detox + Expo issue arises, neither the Detox team nor the Expo team owns the fix.

### Why not Appium

Appium is the most flexible option but carries the highest setup and maintenance cost. It's designed for cross-platform testing across web, mobile, and desktop — power we don't need. For a single Expo app with straightforward UI flows, Appium's WebDriver overhead, verbose test code, and infrastructure requirements are not justified.

## Proof-of-Concept Plan

**Goal:** One working Maestro flow that tests the sign-in happy path.

### Prerequisites

- macOS with Xcode
- Physical iPhone connected via USB cable (our current local setup — see `docs/engineering/ios-dev-build-cable.md`)
- Maestro CLI installed (`brew install maestro`)
- **`idb` (iOS Development Bridge) installed** (`brew tap facebook/fb && brew install idb-companion`) — required for Maestro to communicate with a physical iOS device. Not needed if using iOS Simulator instead.
- Dev client built and installed on the device (`npx expo run:ios --device`)
- Mac and iPhone on the same Wi-Fi, with `EXPO_PUBLIC_SERVER_URL` set to the Mac's LAN IP
- Backend server running (`pnpm infra:up && pnpm dev:server`)
- Metro running (`pnpm dev:mobile`)
- A test user in Clerk with known credentials

### Flow file

```yaml
# e2e/flows/sign-in.yaml
appId: com.conradlabs.mobile
---
- launchApp
- assertVisible: "Sign in"

# Enter credentials
- tapOn: "Email"
- inputText: "testuser@example.com"
- tapOn: "Password"
- inputText: "TestPassword123!"

# Submit
- tapOn: "Sign in"

# Verify we landed on the Home tab
- assertVisible: "Welcome"
```

### Run it

```bash
maestro test e2e/flows/sign-in.yaml
```

### What this validates

- Maestro can launch the Expo dev client on a physical device (our primary local setup)
- It can interact with Clerk's sign-in form (text inputs + button)
- It can verify navigation to the authenticated Home screen
- The full chain works: Maestro -> device -> app -> (LAN) -> backend server -> database

### Adjustments that may be needed

- Element selectors may need `testID` props if text matching is ambiguous
- Clerk's sign-in form may have intermediate loading states — may need `waitForAnimationToEnd` or `extendedWaitUntil`
- If testing on iOS Simulator instead of a physical device, `idb` is not required and `appId` launch behavior may differ slightly
- Physical device tests depend on the Mac firewall allowing port 3000 and both devices being on the same Wi-Fi (already configured per `docs/engineering/ios-dev-build-cable.md`)

## CI Integration Approach

> Full CI pipeline design is out of scope (tracked in the CI/CD spike). This section notes the integration points.

### Option A: macOS GitHub Actions runner

```yaml
# .github/workflows/mobile-e2e.yml (conceptual)
jobs:
  mobile-e2e:
    runs-on: macos-latest          # Required for iOS Simulator
    steps:
      - uses: actions/checkout@v4
      - run: brew install maestro
      - run: # Build or download the .app from EAS
      - run: # Boot iOS Simulator
      - run: maestro test e2e/flows/
```

**Pros:** Full control, works with existing GitHub Actions setup.
**Cons:** macOS runners cost 10x Linux runners. iOS Simulator boot time adds ~2-3 min.

### Option B: Maestro Cloud

```bash
maestro cloud --app-file=build.app e2e/flows/
```

**Pros:** No macOS runner needed. Managed device farm. Free tier available.
**Cons:** External dependency. Upload time for app binary. Potential queue wait.

### Option C: EAS Build + Maestro (via custom build steps)

EAS Build supports custom build steps that can run Maestro flows as part of the build pipeline. This keeps everything in the Expo ecosystem.

**Pros:** Single ecosystem (Expo). No separate CI job.
**Cons:** Ties testing to build pipeline. Less flexible for running tests independently.

**Recommendation for CI:** Start with **Option A** (macOS runner) for simplicity and control. Evaluate Maestro Cloud later if runner costs become a concern. Cross-reference with the CI/CD spike for final pipeline design.
